| KI-30 | High | Password hashing is PBKDF2-HMAC-SHA256 at 600,000 iterations (OWASP guidance). Measured on Node here (`npm run measure:hash`): about 105 ms per hash at 600,000, about 51 ms at 300,000, about 20 ms at 100,000. Workers Free allows about 10 ms CPU per request, so even a weakened setting would likely not fit, and the real figure on workerd is **still unmeasured**. A startup guard now refuses to run below 600,000 iterations (only tests can opt out), so it cannot be weakened by accident. **New compatibility risk:** a 2024 blog post ([lord.technology](https://lord.technology/2024/02/21/hashing-passwords-on-cloudflare-workers.html)) reports that Web Crypto PBKDF2 on Workers is capped at 100,000 iterations; Cloudflare's own Web Crypto page does not mention a limit, and I could not verify it (the workerd issue page was not fetchable). If true, 600,000 cannot run through `crypto.subtle` on Workers at all. The code now **fails closed** when the platform refuses the hash (503 `auth_unavailable`, no account, no session, no weaker hash; `tests/hash.platform.test.mjs` simulates such a cap). Cloudflare documents `node:crypto` (including `scrypt`; `argon2` unsupported) as available with `nodejs_compat`, with no stated parameter or CPU limits: a possible path, untested | `src/auth/service.js`; `scripts/measure-hash.mjs` | Measure in a local Workers runtime, then a founder decision: the Workers Paid plan (higher CPU limit, costs money), a different hosting arrangement for sign-in, or an external identity service. Not solved |
